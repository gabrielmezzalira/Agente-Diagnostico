<objective>
Fatia vertical (tracer) que prova a espinha do handoff gateado por status ponta a ponta: um
relatório discovery nasce com `status='Rascunho'`, é transicionado para `'Aprovado para build'`
por uma rota mínima, e o `import-from-diagnosis` só extrai features quando o status está aprovado —
rejeitando com 422 caso contrário. Sales permanece intocado (coluna nullable, gate no-op quando
`status=None`).

Este plano LIDERA a fase: ele costura a coluna nova (`reports.status`), o grant inicial, a rota de
transição (D-38), o gate no service (D-37) e o SELECT do repositório (Pitfall 5) na fatia mais fina
possível — usando o `generate_report(mode='discovery')` que JÁ existe (o corpo rico do PRD é
expansão da Fase, no plano 04-02). Aqui provamos a arquitetura do handoff antes de investir no
conteúdo do relatório.

Escopo: só backend (readiness/`status`/gate/rota). O front-end (botão "Gerar PRD" + UI de revisão e
aprovação humana) é Fase 5 (D-35) — esta fase entrega apenas a rota de transição que o botão vai chamar.

Purpose: eliminar o risco arquitetural mais alto da fase (o gate de aprovação realmente bloqueia o
import? a coluna aditiva realmente não regride sales?) numa fatia commitável, antes de qualquer
expansão.
Output: migration aplicada + coluna lida no repositório + grant de status + rota PATCH + gate no
service + teste de integração real do gate (REP-02).
</objective>

## Plano da task — 7 seções obrigatórias (CLAUDE.md)

1. **O que muda (linguagem comum):** hoje qualquer relatório pode ser "importado" para a
   precificação a qualquer momento. Este plano cria um "carimbo de aprovação" no relatório de
   discovery: ele nasce como **Rascunho**, alguém precisa mudá-lo para **Aprovado para build**, e só
   então o Precificador aceita puxar as funcionalidades dele. Relatórios de venda (sales) não têm
   carimbo nenhum e continuam funcionando exatamente como antes. É como exigir a assinatura de um
   documento antes de ele virar orçamento — sem assinatura, o orçamento não abre.
2. **Como vai ser alterado:** (Task 2) cria a coluna `status` no banco e faz o repositório lê-la;
   (Task 3) faz o relatório discovery nascer como "Rascunho", cria uma rota para mudar esse carimbo,
   e coloca a trava no serviço do Precificador. Commits atômicos: 1 migration+repo, 1
   grant+rota+gate+teste. Task 2 é mecânica (coluna + select); Task 3 muda comportamento (trava do
   import).
3. **Riscos de cada ação:** migration one-way no banco de produção (Task 2) — coluna errada obriga
   nova migration; select sem `status` (Pitfall 5) faz a trava passar sempre em silêncio; trava mal
   colocada pode regredir o import sales (quebrar REP-03); rota PATCH sem validação aceitaria status
   inventado (Tampering).
4. **Como prevenir:** checkpoint humano antes da migration (Task 1); confirmação no SQL Editor de que
   a coluna existe (Task 2, human-check); teste explícito de que sales (status None) importa sem 422
   (Task 3c); `Literal` de 3 valores na rota (rejeita qualquer outro com 422).
5. **Como consertar (rollback):** migration → `ALTER TABLE reports DROP COLUMN IF EXISTS status;`
   (nova migration de remoção); código → reverter os commits das Tasks 2/3 (`git revert`), o que
   remove o gate e restaura o import atual; nenhuma linha sales foi tocada, então sales volta sozinho.
6. **Decisões que são do time:** aplicar a coluna one-way no Supabase (Task 1, checkpoint). A camada
   do gate (service, não router) segue Pattern 2 do RESEARCH e a regra do CLAUDE.md ("router não toca
   regra de negócio") — se o time preferir o router, PARAR e registrar como DECISÃO EM ABERTO.
7. **Verificação (ponta a ponta):** `test_import_from_diagnosis_gate.py` exercita os 3 caminhos reais
   (bloqueado/aprovado/sales) com stubs; a confirmação humana da coluna fecha o laço no banco real.
</planejamento_task>
