## Color

**Already established CITi theme** (`frontend/src/index.css` `@theme` block) — this phase must
reuse these exact CSS variables, not hex literals, and must not add new ones without strong reason:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg-page` (transparent, sits over the gradient `body` background) / `--color-surface` (`#ffffff`) | Page background, panel backgrounds |
| Secondary (30%) | `--color-surface-2` (`#f5f5f2`), `--color-muted` (`#f0f0ed`), `--color-border-std` (`#e0e0dc`) | Cards, panel borders, hover backgrounds, sidebar/panel chrome |
| Accent (10%) | `--color-accent` (`#50d060`) / `--color-accent-hover` (`#3aac48`), tag pairing `--color-green-bg-tag` (`#e0f2e4`) + `--color-border-green` (`#84d49a`) | Reserved for: primary CTA buttons ("Nova sessão", "Gerar", **new "Gerar PRD"**), the live-connection indicator dot, covered-status bars/dots, block-label tag chips, the **new Produto lens badge** |
| Destructive | `--color-red` (`#cc3333`) / `--color-red-bg` (`#fff2f2`) / `--color-border-red` (`#f0b8b8`) | Destructive actions only: "Encerrar" button, critical red-flag rows, insufficient-budget/error text |
| Secondary semantic (warning) | `--color-yellow` (`#d4880a`) / `--color-yellow-bg` (`#fff8ee`) / `--color-border-yellow` (`#f0d8a0`) | Partial-coverage status, warning-severity red flags, TTL bar mid-range |

**New this phase — Dados lens badge color:** the Produto lens already has a natural home in the
existing accent green (it is the primary/default lens, matching the CTA accent). The Dados lens
(auxiliary) must be visually distinct from Produto but must **not** invade the destructive-red or
warning-yellow semantic slots (those are reserved for severity/status, not lens identity). Use a
**neutral/secondary treatment** for the Dados badge: `bg-[var(--color-muted)]` fill,
`text-[var(--color-text-secondary)]` text, `border-[var(--color-border-std)]` border — the same
neutral-pill pattern already used for "encerrada" / "rascunho" badges in `ProjectDetailPage.tsx`
(lines 267, 353). This keeps the palette closed (zero new hex values) while giving Produto vs
Dados a clear default-vs-neutral visual hierarchy that matches "Produto primary / Dados auxiliary"
from the domain model (LENS-01/LENS-02).

| Lens badge | Fill | Text | Border |
|------------|------|------|--------|
| Produto | `--color-green-bg-tag` | `--color-accent` | `--color-border-green` |
| Dados | `--color-muted` | `--color-text-secondary` | `--color-border-std` |

Accent reserved for: primary CTA buttons, live-indicator dot, covered-status fills, block-label
tag chips, **Produto lens badge only**. Never use accent for the Dados badge — that would blur the
primary/auxiliary distinction the two-agent model relies on (LENS-01/02).

## Implementation Notes (non-visual, for planner/executor — data contracts this UI-SPEC depends on)

These are not design-contract fields but are load-bearing facts discovered during research that
the plan must account for, since they gate whether the visual contract above can even render
correctly:

1. **Block-label vocabulary is 18 entries, not 12.** D-44 in `05-CONTEXT.md` says "estendido para
   os 12 blocos discovery (D-32)" — but D-32 (`llm_pricing_service.py:169,287`) is the
   **Precificador's own 12-block vocabulary** ("Engenharia de Dados", "GenAI/IA", ... "Geral"),
   used only in pricing-extraction LLM prompts. It is a **different taxonomy** from
   `question.block`, which is always one of the **18 `DISCOVERY_AREA_SET` area keys**
   (`coverage_areas.py:91-115`, scoped by lens: 8 Produto keys via `gargalo`…`viabilidade_solucao`,
   10 Dados keys via `qualidade_fontes`…`automacoes` — confirmed at
   `discovery_prompt_builder.py:241`, `scoped.block_enum()`). **Resolution (within the
   Claude's-Discretion grant on exact block labels, D-44):** the frontend's extended `blockLabel`
   map must use the **18 `DISCOVERY_AREA_SET.label` values already defined verbatim** in
   `coverage_areas.py` (e.g. `gargalo` → "Gargalo", `qualidade_fontes` → "Fontes e Qualidade dos
   Dados") — no new copy needs inventing, just port the existing PT labels into the frontend map,
   same as the 8 sales entries today. Do **not** use the Precificador's 12-block vocabulary here;
   it belongs to a different feature (pricing extraction), not question sub-labels.
2. **Red flags never get a block sub-label.** The backend `RedFlag` dataclass
   (`session_state.py:68-79`) has no `block` field — only `id`, `text`, `severity`, `evidence`,
   `detected_at`, `lens`. So D-44's "bloco temático vira sub-label" applies to **question cards
   only**; red-flag rows get the lens badge alone, no sub-label under it.
3. **`ReportResponse` (backend Pydantic model, `backend/app/models/sessions.py:22-27`) does not
   declare a `status` field**, even though the `reports` table has had a `status` column since
   Phase 4 (D-36) and the `!isActive` approval UI (D-48) needs to read/display it. Because FastAPI
   filters response bodies against `response_model`, the existing `PATCH /{id}/report` and
   `GET`/`POST` report endpoints currently **strip `status` out of the JSON response** even though
   the DB row has it. The plan must add `status: Literal["Rascunho", "Em revisão", "Aprovado para
   build"]` to `ReportResponse` — this is a small, additive fix inside the same file D-49 already
   authorizes touching, not new backend scope.
4. **Frontend `Report` type (`frontend/src/lib/api.ts:81-87`) also lacks `status`** — add it,
   mirroring the backend fix above, so `finishedReport.status` is typed and available to the new
   approval selector.
5. **`GET /sessions/{id}/readiness` response shape (D-49, Claude's Discretion on exact shape):**
   return the `ReadinessScore` dataclass fields verbatim (`session_state.py:97-108`) — no
   reshaping needed, the dataclass already carries exactly what the UI needs:
   ```json
   { "score": 0.42, "signals": { "cobertura_por_lente": 0.3, "cobertura_global": 0.5, "perguntas_transcricao": 0.6, "secoes_chave": 0.25 }, "ready": false, "low_signals": ["cobertura_por_lente", "secoes_chave"] }
   ```
   `score` is 0–1 (multiply by 100 for the "%" copy); `ready` gates the button's `disabled`;
   `low_signals` feeds the tooltip via the Signal Labels table above.
6. **Mode-inference helper (D-42) is two different code paths, not one function** — the monitoring
   screen infers from the WS payload (`lens != null` anywhere in `coverage`), the project page
   reads `project.mode` directly. Do not build a single shared "detect mode" helper that tries to
   cover both call sites with one signature; keep them as two small, separately-testable checks per
   D-42's own "Nuance por superfície" wording.
7. **Topbar "Relatório" button in `SessionActivePage`** (`:941-949`): in discovery mode, PRD
   generation moves to `ProjectDetailPage` (D-47). Recommended resolution (Claude's Discretion,
   not explicitly locked): hide this topbar button when `mode === 'discovery'` on the **active**
   session view only, to avoid two competing "generate the report" affordances; leave it exactly
   as-is for sales sessions (byte-identical, D-03/D-24).
