## Plano em 7 secoes (obrigatorio — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
O "quanto a reuniao ja rendeu para gerar o documento" (readiness) ja e **calculado** pelo sistema desde a
Fase 4, mas **ninguem consegue perguntar isso pela web** — falta uma "portinha" (endpoint) que responda
esse numero. Esta parte abre essa portinha: `GET .../readiness` devolve a porcentagem e o que ainda falta.
Tambem conserta um detalhe silencioso: o "status do relatorio" (Rascunho / Em revisao / Aprovado para
build) ja e gravado no banco, mas o sistema estava **escondendo esse campo** na resposta da API por
esquecimento no molde (schema) — a gente declara o campo para ele voltar a aparecer. Por fim, ensina o
front a usar essas duas portas. E tudo **aditivo** — nao muda nada do que ja funciona; nao mexe no banco.

**2. Como vai ser alterado**
- **Task 1 (correcao aditiva isolada):** `backend/app/models/sessions.py` — adicionar `status` (Optional
  Literal) em `ReportResponse`. Commit proprio (nao misturar com refator, CLAUDE.md).
- **Task 2 (rota nova + teste):** `backend/app/routers/sessions.py` — `GET /{session_id}/readiness` reusando
  `pipeline_manager.get_or_create(..., allow_finished=True)` + 404; `backend/tests/test_readiness_route.py`.
- **Task 3 (client):** `frontend/src/lib/api.ts` — `Readiness`, `Report.status`, `getReadiness`,
  `updateReportStatus`.

**3. Riscos de cada acao**
- `ReportResponse.status`: risco de **quebrar respostas existentes** se linhas antigas de `reports` nao
  tiverem `status` (Literal sem default => 422 na serializacao). No discovery a coluna sempre e preenchida
  (grant D-36); mas relatorios **sales** nao gravam `status`.
- Rota nova: risco de **vazar dado** de sessao (blind id) ou usar lookup diferente do padrao; risco de
  `get_or_create` rebuildar pipeline encerrado (custo) — aceitavel, e o mesmo precedente do POST /report.
- Client: risco de **tipo divergente** do backend (shape do Readiness).

**4. Como prevenir**
- Investigar o preenchimento de `status`: relatorios sales podem ter `status` nulo. Para nao quebrar o
  sales (REP-03), declarar `status` como `Optional[Literal[...]] = None` (aceita ausencia/None) — mantem o
  discovery com os 3 valores e o sales com None, sem 422. **DECISAO DE IMPLEMENTACAO registrada aqui**:
  usar `Optional[...] = None`, nao Literal obrigatorio, exatamente para preservar sales byte-identico.
- Rota: reusar `get_or_create` + 404 identico aos GET existentes; `test_readiness_route.py` cobre 404 +
  200 (4 campos).
- Client: `Readiness` espelha `ReadinessScore` verbatim (score, signals, ready, low_signals); `tsc -b`.

**5. Como consertar (rollback)**
3 commits atomicos e independentes. Reverter a Task 2 remove a rota + teste (front ainda nao a usa nesta
wave). Reverter a Task 1 volta o `ReportResponse` sem `status`. Reverter a Task 3 remove os metodos/tipos
do client. Nenhum toca banco (sem migration).

**6. Decisoes que sao do usuario/time**
Sem decisao irreversivel. **Registrado como escolha de implementacao** (nao em aberto, mas sinalizada):
`ReportResponse.status` como `Optional[Literal[...]] = None` para nao regredir sales. Delegado ao executor
(CONTEXT): shape exato da resposta de readiness (mantido = campos de `ReadinessScore`) e se a rota usa ou
nao `response_model` (o padrao do arquivo aceita retornar a dataclass direto). Nao criar migration, nao
tocar o gate de import (D-37 ja existe).

**7. Verificacao (ponta a ponta)**
`cd backend && python -m pytest tests/test_readiness_route.py -x -q` prova 200 com os 4 campos + 404;
`python -c` confirma `status` em `ReportResponse.model_fields`; `cd frontend && npx tsc -b --noEmit`
compila o client com os metodos novos.
