## Plano de mudança — leitura para todo o time (7 seções obrigatórias, CLAUDE.md)

### 1. O que muda (em linguagem comum)
Este é o fechamento. Ligamos os dois últimos pontos que ainda tinham "fotocópia" da lista de áreas: o
arquivo que monta o estado da sessão (`session_state.py`) e um prompt de extração de contexto
(`structured_context.py`). Um cuidado especial: em `session_state.py` existe um mecanismo que permite
adicionar "áreas personalizadas" por projeto (o gancho `custom_areas`). Ele NÃO pode ser tocado —
apenas trocamos de onde vem a lista das 8 áreas padrão. Provamos que áreas personalizadas continuam
funcionando com um teste dedicado. No fim, rodamos uma busca no repositório inteiro para garantir que
a lista das 8 áreas não aparece "chumbada" em nenhum outro arquivo — só no arquivo dono. Para o usuário,
zero diferença.

### 2. Como vai ser alterado
Dois commits atômicos:
- **Commit 1 (Task 1):** em `session_state.py`, a lista `COVERAGE_AREAS` sai e o primeiro laço de
  `_init_coverage` passa a iterar `SALES_AREA_SET.keys()`; o import de `AREAS_BY_PROJECT_TYPE` aponta
  direto ao registro. O segundo laço (`custom_areas`, linhas 29-32) fica INTOCADO. Cria
  `test_session_state_custom_areas.py`.
- **Commit 2 (Task 2):** em `structured_context.py`, a linha do block enum dentro do `_EXTRACTOR_SYSTEM`
  passa a ser montada por concatenação com `" | ".join(SALES_AREA_SET.keys())`. Estende o teste golden
  e adiciona os "portões" de busca (grep) que provam fonte única.

### 3. Riscos de cada ação
- **Task 1 — quebrar o merge de custom_areas (D-04 / Pitfall 2):** se a lista padrão e as áreas
  personalizadas forem misturadas no MESMO laço, a ordem de inserção do dicionário muda e qualquer
  consumidor que dependa da ordem (`coverage_to_dict`) vê áreas intercaladas de forma diferente.
- **Task 2 — f-string quebrando as chaves JSON:** `_EXTRACTOR_SYSTEM` é uma string tripla comum que
  contém literais `{` e `}` (um exemplo de JSON). Convertê-la em f-string para interpolar as chaves
  quebraria essas `{ }` (precisariam ser escapadas) e pode alterar bytes silenciosamente.
- **Task 2 — indentação/nova-linha:** a linha do enum tem indentação de 2 espaços e uma quebra de linha
  ao final; perdê-las viola o byte-a-byte.

### 4. Como prevenir
- **Task 1:** manter o formato de dois laços EXATAMENTE como está; mudar só a fonte do primeiro laço
  (`COVERAGE_AREAS` → `SALES_AREA_SET.keys()`); NÃO tocar nas linhas 29-32. O teste
  `test_session_state_custom_areas.py` é a rede de proteção do D-04.
- **Task 2:** NÃO transformar `_EXTRACTOR_SYSTEM` em f-string. Montar por concatenação:
  `prefixo + "  " + " | ".join(SALES_AREA_SET.keys()) + "\n" + sufixo`, preservando os dois trechos
  estáticos (incluindo as chaves JSON literais) intactos. Asserção golden de igualdade da linha exata.

### 5. Como consertar (plano de rollback)
- Commits atômicos por arquivo. `git revert` do commit do Task 1 restaura `COVERAGE_AREAS` e o import
  antigo; `git revert` do Task 2 restaura o `_EXTRACTOR_SYSTEM` original. Sem banco, sem config externa.

### 6. Decisões que são do usuário/time (DECISÕES EM ABERTO)
- **`pipeline.py` (linhas 325, 452) — `block=q_data.get("block", "negocio")`:** NÃO é uma lista das 8
  áreas, é um único valor default de dicionário. RESEARCH.md/PATTERNS.md classificam como fora de
  escopo (não é um dos 3 arquivos canônicos e não é uma duplicação da lista). **Decisão registrada:
  fora de escopo desta fase** — não tocar em `pipeline.py`. Se o time quiser consistência total no
  futuro, é uma mudança opcional trivial, mas não é exigida por D-01/D-02/D-03.
- **`structured_context.py` estava fora dos 3 arquivos canônicos do CONTEXT.md** (Open Question 1).
  Decisão registrada: **incluído nesta fase** (recomendação da RESEARCH.md) — remove a 4ª duplicata do
  backend em vez de deixá-la como dívida silenciosa. Nenhuma decisão de time pendente.
