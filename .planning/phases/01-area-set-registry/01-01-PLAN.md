Este plano (1) congela a saída atual num teste golden **antes** de qualquer mudança, e (2) cria o
módulo `coverage_areas.py` (fonte única de verdade) e reconecta **um** consumidor — o schema de
`classify_coverage` em `llm.py` — provando que a saída continua byte-a-byte idêntica.

Purpose: um refactor de "mudança zero" só é seguro se a saída pré-refactor estiver congelada como
fixture ANTES de mexer no código (D-03). O tracer prova, no primeiro commit de refactor, que o seam
do registro → prompt → Gemini funciona sem alterar um único byte, antes de expandir para os demais
consumidores nos planos 02 e 03.

Output: `backend/app/services/coverage_areas.py` (registro leaf), o arquivo de teste golden com

## Plano de mudança — leitura para todo o time (7 seções obrigatórias, CLAUDE.md)

### 1. O que muda (em linguagem comum)
Hoje a lista das 8 "áreas de cobertura" do modo vendas (negócio, engenharia de dados, visualização,
etc.) está **copiada e colada** em vários arquivos do backend. Isso é frágil: mudar uma vírgula num
lugar e esquecer noutro quebra silenciosamente o comportamento. Vamos criar **um único arquivo**
(`coverage_areas.py`) que passa a ser o "dono" dessa lista — como ter uma única fonte oficial em vez
de várias fotocópias divergentes. Neste primeiro plano fazemos isso com cuidado extremo: **antes** de
mexer em qualquer coisa, tiramos uma "foto" (teste golden) do texto exato que o sistema gera hoje.
Depois criamos o arquivo dono e ligamos **apenas um** consumidor a ele, conferindo que a foto continua
idêntica letra por letra. Nada que o cliente/usuário vê muda — é pura reorganização interna.

### 2. Como vai ser alterado
Dois commits atômicos, nesta ordem:
- **Commit 1 (Task 1):** cria `backend/tests/test_coverage_areas_golden.py` + `backend/tests/fixtures/`
  e faz os testes passarem **contra o código atual** (sem nenhuma mudança de produção). Congela o texto
  atual como fixture.
- **Commit 2 (Task 2):** cria `backend/app/services/coverage_areas.py` (novo arquivo, módulo leaf) e
  reescreve **um** ponto em `llm.py` (`classify_coverage`) para ler o schema do registro. Roda o teste
  golden de novo: tem que continuar verde.

### 3. Riscos de cada ação
- **Task 1 — foto errada:** se a fixture for capturada de forma incorreta (ex.: rodando um código já
  alterado), ela "congela" o texto errado e o refactor inteiro fica sem rede de proteção.
- **Task 2 — schema diferente por um byte:** o schema é texto que vai dentro do prompt do Gemini.
  Uma vírgula, aspa ou espaço a mais muda a resposta do LLM (viola o Critério de Sucesso #1).
- **Task 2 — import circular:** se `coverage_areas.py` importar de `llm.py`/`prompt_builder.py`/
  `session_state.py`, o backend não sobe (`ImportError` na inicialização — Pitfall 3).

### 4. Como prevenir
- **Task 1:** capturar a fixture rodando **o código atual, ainda intocado**, e commitar o teste verde
  como o **primeiro** commit, isolado (nunca junto do refactor).
- **Task 2:** asserção de igualdade de string exata (`==`) contra o literal citado verbatim na
  RESEARCH.md — nunca inspeção visual. `schema_json` é construído por concatenação de string (NÃO
  `json.dumps` — o texto tem `"score":0-100`, que não é JSON válido).
- **Task 2:** `coverage_areas.py` importa só `dataclasses` (stdlib), zero imports de `app.services.*`.

### 5. Como consertar (plano de rollback)
- Cada task é um commit atômico e independente. Se o Task 2 quebrar o teste golden, `git revert` do
  commit do Task 2 restaura o estado pré-registro sem tocar na fixture (que veio no commit do Task 1).
- Se a fixture do Task 1 estiver errada, `git revert` do commit do Task 1 e recapturar.
- Nenhuma mudança de banco, config externa ou contrato de API — rollback é puramente `git revert`.

### 6. Decisões que são do usuário/time (DECISÕES EM ABERTO)
- Nenhuma decisão irreversível ou de estratégia neste plano. A **forma** do registro (D-01) é marcada
  como *costly* (vira o contrato que as Fases 2/3 consomem), mas é totalmente reversível por git dentro
  desta fase — não é uma porta de mão única, não exige aprovação de checkpoint.
- Deletar o modo vendas / CITI_PORTFOLIO permanece **fora de escopo** (decisão de time deferida).

### 7. Verificação (ponta a ponta)
`cd backend && python -m pytest tests/test_coverage_areas_golden.py -q` deve passar verde tanto após o
Commit 1 (contra código atual) quanto após o Commit 2 (com o registro ligado). O teste prova que o
system prompt de `classify_coverage` é idêntico letra por letra antes e depois.

## Singular → Plural transition (advisory, non-blocking)
This phase generalizes a single hardcoded 8-area list into NAMED AREA SETS (D-01). The now-primary noun
is the **named area set** (`SALES_AREA_SET`, a keyed `AreaSet`), not "the area list".
- **Decision:** PROMOTE — the registry is designed around named area sets from the start, not a single
  set with a second bolted on later.
- **Rationale:** Phase 2's discovery area set (11 areas, Produto + Dados lenses) and Phase 3's lens
  tagging build directly on this shape; designing around named sets now makes the discovery set a
  trivial addition (roadmap Success Criterion #4). This is exactly D-01.
- **Suggested invariant (implemented as the subset unit test in plan 02, NOT a runtime assertion):**
  `AREAS_BY_PROJECT_TYPE` keys are a subset of `SALES_AREA_SET.keys()` (RESEARCH Open Question 2).
</assumption_delta_decision>
