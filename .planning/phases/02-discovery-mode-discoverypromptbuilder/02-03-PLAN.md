<objective>
Tornar o `mode` configurável e persistente ponta a ponta: a coluna `projects.mode` no Supabase
(D-07), o campo `mode` nos modelos Pydantic (`ProjectCreate/Update/Response`), e um toggle mínimo
`sales|discovery` no formulário de projeto (D-11). É a fatia "configurar discovery" (DB → API → UI)
que fecha DISC-01. Fecha o ciclo do `mode` que o fork de 02-01 consome em runtime.

Purpose: DISC-01 — um projeto pode ser criado/editado em `mode=discovery` (vs `sales`) sem afetar os
projetos sales existentes (que ficam `sales` por DEFAULT, sem backfill).
Output: migration aditiva idempotente; `ProjectMode` + `mode` nos três schemas; toggle no
`ProjectFormPage.tsx` + `mode` em `Project`/`ProjectCreate` (api.ts).

**A coluna `mode` é one-way (D-07):** criar coluna nova no Supabase exige migration de remoção para
reverter e afeta o contrato da API `/projects`. Por isso a Task 1 é um `checkpoint:decision` que
trava a decisão antes de escrever/aplicar a migration.
</objective>

## Plano de execução — 7 seções obrigatórias (CLAUDE.md)

**1. O que muda (em linguagem comum)**
Hoje todo projeto é, na prática, um projeto de vendas — não existe nem onde guardar "que tipo de
reunião é esta". Este plano cria esse liga/desliga: uma coluna nova no banco (`mode`), o mesmo campo
nos contratos da API, e um botão de rádio no formulário do projeto ("Vendas" ou "Discovery"). Os
projetos que já existem continuam sendo "Vendas" automaticamente — ninguém precisa mexer neles.
Como adicionar um campo "tipo de atendimento" numa ficha de cliente: fichas antigas ganham o valor
padrão sozinhas.

**2. Como vai ser alterado (arquivos, ordem, commits atômicos)**
Ordem: Task 1 (checkpoint de decisão, one-way) → Task 2 (migration + schemas + teste) → Task 3
(aplicar a migration no Supabase, BLOCKING) → Task 4 (toggle no frontend). Commits atômicos:
migration+schemas+teste num commit; frontend num commit separado. A aplicação da migration é um passo
operacional (não é commit de código).

**3. Riscos de cada ação**
- Task 2: usar CHECK/enum nativo divergiria do padrão do repo; errar o default quebraria o SC#4.
  Adicionar um `ProjectRepository` "de brinde" seria refactor não pedido (Pitfall 5).
- Task 3: aplicar no banco é one-way; sem aplicar, a verificação ponta a ponta vira falso-positivo
  (o Pydantic aceita `mode`, mas a coluna não existe → pipeline lê None).
- Task 4: campo `mode` sem casar com os tipos quebra o build; esquecer a carga defensiva no `useEffect`
  faria a edição perder o mode salvo.

**4. Como prevenir**
- Task 2: seguir o analog `add_tunnel_url.sql` (ADD COLUMN IF NOT EXISTS + DEFAULT); default `'sales'`;
  teste puro de Pydantic (default sales, discovery aceito, valor inválido → ValidationError). Não
  criar repository.
- Task 3: gatear com o checkpoint da Task 1; usar `ADD COLUMN IF NOT EXISTS` (reaplicar é seguro);
  conferir `information_schema` e ausência de `mode NULL` após aplicar.
- Task 4: `npm run build` (tsc) valida os tipos; replicar o padrão defensivo de `source` no `useEffect`.

**5. Como consertar (rollback)**
- Código: `git revert <sha>` dos commits de migration+schemas e do frontend restaura o estado
  anterior; com `ProjectUpdate.mode = None` e `ProjectCreate.mode` default `'sales'`, o contrato
  volta a se comportar como antes.
- Banco (one-way): reverter a coluna exige uma nova migration `ALTER TABLE projects DROP COLUMN IF
  EXISTS mode;` — decisão do time (a coluna guarda dado de projetos discovery já criados). Por ser
  one-way, essa saída de emergência está registrada aqui mas só é executada com aval do time.

**6. Decisões que são do usuário/time (DECISÃO EM ABERTO)**
- **Task 1 é o ponto de parada obrigatório:** criar a coluna one-way `projects.mode` precisa de aval
  explícito (formato `text DEFAULT 'sales'` sem CHECK). Se o time exigir CHECK/enum nativo, ajustar
  antes de aplicar.
- **Aplicação da migration (Task 3):** depende de acesso ao Supabase (fora do repo) — se indisponível
  nesta execução, PARAR e sinalizar intervenção manual.

**7. Verificação (ponta a ponta)**
Automático: `cd backend && python -m pytest tests/test_projects.py -q` (default sales, discovery
aceito, inválido rejeitado) + `cd frontend && npm run build` (tipos do toggle). Banco (humano, Task 3):
`information_schema` mostra a coluna `mode` com default `'sales'` e nenhuma linha `mode NULL`. Manual
(em /gsd-verify-work): no app, criar um projeto marcando "Discovery", salvar, reabrir em edição e
confirmar que o toggle volta em "Discovery"; criar outro em "Vendas" e confirmar que segue vendas.
