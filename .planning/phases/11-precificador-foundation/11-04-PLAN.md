## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input → PricingEditorPage | Numeric inputs (horas, ticket_price, num_analysts) must be validated before sending to API |
| Frontend approval action → POST /pricings/:id/approve | Action is irreversible from UI; no confirmation modal needed per CONTEXT.md (user decision: simple button) |
| Optimistic updates → API sync | On update failure, hook throws; page must handle error without corrupting local state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-04-01 | Tampering | Inline feature edit — horas: negative or zero value accepted in number input | mitigate | Backend validator in PricingFeatureCreate rejects horas <= 0 (implemented in plan 11-03); frontend shows API error via error state |
| T-11-04-02 | Tampering | Approved pricing inputs shown as editable in DOM if status guard fails | mitigate | PricingEditorPage checks pricing.status === 'approved' to set inputs disabled; Aprovar button is also disabled; backend PUT /pricings/:id does not enforce approved guard (edit blocked only by frontend — acceptable for single-user tool) |
| T-11-04-03 | Information Disclosure | calculatePricing() runs client-side; formula is visible to users | accept | Formulas are not sensitive business logic; calculation is a feature, not a secret |
| T-11-04-04 | Denial of Service | usePricing useEffect fires calculatePricing on every feature/pricing state change | accept | calculatePricing is pure O(n) function with no I/O; no debounce needed; n is bounded by practical feature list size |
| T-11-SC | Tampering | No new npm packages in this plan | accept | All required packages (react-router-dom, lucide-react) already installed |
</threat_model>
