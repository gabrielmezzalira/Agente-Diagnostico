<objective>
Builds the entire Precificador backend following SOLID layered architecture (router → service → repository → Supabase). Pydantic models for pricings and pricing_features, PricingRepository for all DB access, PricingService for business logic (including approved-status guards), and thin routers that only call service methods. Registers new routers in main.py. Calculated outputs are computed on-read by PricingCalculator — never stored in the pricings table.

Purpose: After this plan, the backend is fully functional with correct separation of concerns. Plan 11-04 can consume these endpoints to build the frontend editor. This plan runs in parallel with 11-02 (no shared files).

Output: 6 new backend files (models, repository, service, 2 routers), 2 extended registration files, full REST API for pricings.

SOLID enforcement:
- Routers: HTTP plumbing only. No db.table() calls. No business logic. Calls PricingService.
- Services: Orchestrate business logic. No db.table() calls. Calls PricingRepository and PricingCalculator.
- Repositories: Only layer with db.table() calls. No business logic. Returns plain dicts or lists.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → POST /pricings/:id/approve | Action is irreversible — approved pricings become read-only snapshots |
| Client → DELETE /pricings/:id | Delete must be blocked for approved pricings to preserve history integrity |
| Client → PUT /pricings/:id | Update must be blocked for approved pricings — service raises 409 |
| Client → pricing_history | Snapshots are immutable; inserts only, no updates or deletes exposed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-03-01 | Tampering | DELETE /pricings/:id on approved pricing | mitigate | 409 guard in PricingService.delete_pricing: if status == "approved" raise HTTP 409; approved snapshots remain in pricing_history |
| T-11-03-02 | Tampering | PUT /pricings/:id on approved pricing | mitigate | 409 guard in PricingService.update_pricing: if status == "approved" raise HTTP 409 "Cannot modify an approved pricing" — mirrors delete guard |
| T-11-03-03 | Tampering | POST /pricings/:id/approve called twice | mitigate | 409 guard in PricingService.approve_pricing: if already approved raise HTTP 409 "Already approved" |
| T-11-03-04 | Tampering | pricing_history.snapshot can be manually updated in Supabase | accept | No API update endpoint for pricing_history; history is append-only from the API perspective; manual DB access requires service-role credentials |
| T-11-03-05 | Elevation of Privilege | project_id in POST body could reference another user's project | accept | Single-user deployment (per REQUIREMENTS.md v2 deferred: multi-user); no row-level security required in v2.0 |
| T-11-03-06 | Denial of Service | Large feature lists passed to PricingCalculator | accept | Calculation is O(n) summation with no external calls; no practical DoS surface for single-user tool |
| T-11-SC | Tampering | No new pip installs in this plan | accept | All packages used (fastapi, supabase) already installed; LangChain deferred to Phase 12 |
</threat_model>
