## Plano de execução — 7 seções obrigatórias (CLAUDE.md)

**1. O que muda (em linguagem comum)**
Este plano coloca a etiqueta de lente ("Produto" ou "Dados") em mais dois lugares: nos alertas
(red flags) e nas áreas de cobertura mostradas na tela de discovery. Para os alertas, o mesmo detector
de hoje (continua um só) passa a dizer de qual lente é cada alerta; se ele esquecer ou responder algo
estranho, o sistema assume "Produto" por padrão. Para as áreas de cobertura, a etiqueta vem da lista
oficial de áreas (o registro), não de um palpite em tempo real. As reuniões de vendas continuam sem
etiqueta nenhuma — tudo com lente vazia.

**2. Como vai ser alterado (arquivos, ordem, commits atômicos)**
Ordem: Task 1 (lente nos red flags — dataclass + prompt + parser com fallback) num commit; Task 2
(lente nas áreas — reescrever `coverage_to_dict`) em outro commit. Cada um é mudança de comportamento
(só no discovery) e está sinalizado como tal — nada de refactor misturado.

**3. Riscos de cada ação**
- Task 1: inserir o valor bruto de `lens` do LLM sem allowlist deixaria uma resposta malformada gravar
  lente arbitrária no banco (Tampering/V5). Indexação direta `flag["lens"]` quebraria no sales (que não
  devolve o campo). Rodar o detector 2× criaria um 2º detector (fora de escopo).
- Task 2: ler `c.lens` do `CoverageArea` runtime daria `AttributeError` (Pitfall 3) — a lente é do
  registro estático, não do estado.

**4. Como prevenir**
- Task 1: allowlist estrita `raw_lens in ("produto","dados") else "produto"` (D-22); `.get("lens","")`
  sempre; gate `mode=="discovery"`; detector chamado uma única vez (teste sales confirma 1 chamada e
  lens None).
- Task 2: derivar `lens` de `DISCOVERY_AREA_SET`/`SALES_AREA_SET` por `mode` via `lens_by_key.get(area)`
  (None para custom e sales); nunca adicionar `lens` ao `CoverageArea` runtime.

**5. Como consertar (rollback)**
- `git revert <sha>` de cada commit: reverter a Task 2 volta `coverage_to_dict` ao formato sem `lens`;
  reverter a Task 1 remove o campo do red flag e a instrução do prompt. Como tudo é gateado por
  `mode=="discovery"` e os campos são aditivos (default None), reverter não afeta sessões sales.

**6. Decisões que são do usuário/time (DECISÃO EM ABERTO)**
- **Texto exato da instrução de classificação da lente** no prompt do red flag detector é
  discricionário (análogo a D-10) — ajustável depois sem tocar o contrato JSON. Nenhuma decisão
  irreversível neste plano (as colunas do banco são do 03-02, com checkpoint próprio).

**7. Verificação (ponta a ponta)**
Automático: `cd backend && python -m pytest tests/test_two_agent_lens.py -q` (red flag lens + fallback
+ sales None; coverage lens discovery/sales/custom) e a suíte golden/discovery das Fases 1-2. Manual
(em /gsd-verify-work): sessão discovery real → inspecionar os frames `red_flag` (cada um com
`lens`) e `coverage_update` (cada área com `lens` produto/dados); numa sessão sales, confirmar `lens`
ausente/None.

| transcrição (LLM input) → backend | A transcrição não confiável pode influenciar a lente que o LLM devolve no red flag |
