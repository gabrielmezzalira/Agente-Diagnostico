## Plano de execução — 7 seções obrigatórias (CLAUDE.md)

**1. O que muda (em linguagem comum)**
Para o sistema "lembrar" de qual assistente veio cada pergunta e cada alerta, precisamos de um lugar
para guardar essa etiqueta no banco de dados. Este plano abre duas colunas novas ("lens") nas tabelas
de perguntas e de alertas, e deixa uma nota explicando os dois novos nomes de agente. É como
acrescentar uma coluna "categoria" numa planilha: as linhas antigas simplesmente ficam com a célula
vazia, sem nada quebrar. As reuniões de vendas continuam com essa célula vazia — nada muda para elas.

**2. Como vai ser alterado (arquivos, ordem, commits atômicos)**
Ordem: Task 1 (checkpoint de decisão, one-way) → Task 2 (escrever a migration + o campo `lens` na
resposta da API, num commit) → Task 3 (aplicar a migration no Supabase — passo operacional, não é
commit). A migration é uma mudança de schema aditiva; o campo `lens` no `QuestionResponse` é
mecânico (copia o padrão do `block`).

**3. Riscos de cada ação**
- Task 2: pôr DEFAULT na coluna faria sales gravar um valor em vez de NULL (quebra D-18); dividir em
  migrations separadas poderia aplicar só uma tabela e o código quebraria ao gravar a outra
  (DoS indireto); um `ALTER TYPE` inexistente em `session_prompts.agent` daria erro (não é enum nativo).
- Task 3: aplicar no banco é one-way; sem aplicar, os inserts de `lens` falham em produção enquanto os
  testes (fake DB) enganosamente passam.

**4. Como prevenir**
- Task 2: seguir o analog `20260921000000_add_mode_to_projects.sql` (ADD COLUMN IF NOT EXISTS, mas SEM
  DEFAULT); migration única cobrindo as 3 mudanças; só `COMMENT` em session_prompts.agent (sem
  ALTER TYPE/CHECK). Verificações por grep garantem as duas colunas, o comentário e a ausência de
  ALTER TYPE.
- Task 3: gatear com o checkpoint da Task 1; `ADD COLUMN IF NOT EXISTS` torna reaplicar seguro;
  conferir `information_schema` (duas linhas) e ausência de `lens` não-nulo em linhas sales antigas.

**5. Como consertar (rollback)**
- Código: `git revert <sha>` do commit de migration+schema restaura o estado anterior (o campo `lens`
  no `QuestionResponse` é opcional; sua ausência não quebra a API).
- Banco (one-way): reverter as colunas exige uma nova migration `ALTER TABLE questions DROP COLUMN IF
  EXISTS lens;` e idem `red_flags` — decisão do time (as colunas guardam dado de sessões discovery já
  gravadas). Registrado aqui como saída de emergência, executado só com aval do time.

**6. Decisões que são do usuário/time (DECISÃO EM ABERTO)**
- **Task 1 é o ponto de parada obrigatório:** criar as colunas one-way `lens` precisa de aval explícito
  (formato `text` nullable sem CHECK, recomendado). Se o time exigir CHECK, ajustar a migration antes
  de aplicar.
- **Aplicação da migration (Task 3):** depende de acesso ao Supabase (fora do repo) — se indisponível
  nesta execução, PARAR e sinalizar intervenção manual.

**7. Verificação (ponta a ponta)**
Automático: `QuestionResponse` importável com o campo `lens`; a migration existe com as duas colunas
aditivas, o COMMENT dos novos agentes, e zero `ALTER TYPE`. Banco (humano, Task 3): `information_schema`
mostra `lens` em `questions` e `red_flags`, e linhas antigas com `lens` NULL. Manual (em
/gsd-verify-work): após aplicar, abrir uma sessão discovery, gerar perguntas/alertas e confirmar no
banco que as linhas novas gravam `lens` produto/dados enquanto as de sales ficam NULL.
