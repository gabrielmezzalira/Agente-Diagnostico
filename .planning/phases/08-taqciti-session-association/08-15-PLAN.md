## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
Quando a Taqciti cria uma sessão no Agente para uma reunião, o Agente liga o "cérebro" dela e fica chamando a
IA periodicamente. Hoje só o web app desliga esse cérebro (botão "Encerrar"). Para as sessões que a Taqciti
cria, ninguém desliga — o custo continua correndo depois da reunião. O time precisa decidir quem desliga e
quando (B4-b). A recomendação é: a própria Taqciti, 10 minutos depois do fim da reunião (o tempo em que a
pessoa ainda pode voltar para a mesma sala) e só quando não houver mais falas esperando para sair. Para isso o
backend precisa de uma "porta de desligar" própria da extensão — é o que este plano cria, se o time aprovar.

**2. Como vai ser alterado**
- Task 1: `checkpoint:decision` B4-b.
- Task 2 (commit): `ExtensionRepository` ganha `get_session` e `mark_session_finished`; `ExtensionSessionService`
  ganha `finish_session` (regras 404/409 + `pipeline_manager.stop_session`); `extension_clients.py` ganha a rota;
  testes estendidos. `sessions.py` (finish do web app) NÃO é tocado nem refatorado.

**3. Riscos de cada ação**
- Task 1 — decidir pelo time (contrato novo + mudança de manifesto + custo).
- Task 2 — encerrar uma sessão de outra origem (recall/web) por engano ou por chamada forjada.
- Task 2 — encerrar e não parar o pipeline (o custo continua) ou parar o pipeline e falhar ao gravar.
- Task 2 — duplicar a lógica do finish do web app e as duas divergirem.
- Task 2 — acesso ao banco no router.
- Task 2 — rodar sem que os arquivos do 08-07/08-12 existam (B1 rejeitada ou com ajustes) e o executor improvisar o
  repositório/service/router.

**4. Como prevenir**
- Task 1 com `gate="blocking-human"`.
- `finish_session` checa `source == "extension"` e `status == "active"` antes de gravar; testes de 404/409.
- Grava `finished` primeiro e chama `stop_session` (idempotente, já testado); falha no `stop_session` vai para o
  log sem desfazer a gravação (mesmo padrão do finish do web app).
- Reimplementação mínima e só do caminho `extension` (sem Recall/tunnel), com comentário apontando o finish do
  web app como referência — refatorar o `sessions.py` para um service comum é outra task (CLAUDE.md: refator ≠
  feature); registrado como dívida.
- Router só chama `service.finish_session`; grep negativo de `db.table` no router.
- A pré-condição da Task 2 lê também o 08-07-SUMMARY (B1 = aprovar-recomendado); sem ele, a task não executa.

**5. Como consertar (plano de rollback)**
- `git revert <sha-task-2>` remove a rota; sessões já encerradas por ela continuam encerradas (podem ser vistas no
  web app). Em produção, novo deploy.

**6. Decisões que são do usuário/time**
- **DECISÃO EM ABERTO B4-b — PARAR na Task 1 até o time decidir** (quem encerra, quando, a permissão `alarms` e a
  aceitação do resíduo "sessão em Envio parou não é encerrada sozinha").
- Pré-condição cruzada: a Task 2 estende arquivos criados pelo 08-07/08-12, que só existem com B1 =
  aprovar-recomendado; por isso ela confere também o 08-07-SUMMARY.
- Dívida registrada (não bloqueante): unificar o finish do web app e o da extensão num service comum — refator
  futuro, decisão do time.

**7. Verificação (ponta a ponta)**
