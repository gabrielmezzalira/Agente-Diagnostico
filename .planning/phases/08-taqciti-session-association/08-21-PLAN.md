## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
Nada de código novo: é a "vistoria final". Primeiro, todas as verificações automáticas rodam juntas e o resultado
fica anotado no documento de validação da fase. Depois, uma pessoa do time faz o teste de verdade, numa reunião do
Google Meet, seguindo um roteiro: enviar uma reunião guardada no fim, derrubar o Agente no meio e ver o reenvio,
descartar com confirmação, e escolher o cliente no meio da reunião — além de conferir o visual em telas pequenas.

**2. Como vai ser alterado**
- Task 1: rodar o portão automático e atualizar o mapa de verificação em `08-VALIDATION.md` (status por task,
  `wave_0_complete`, assinatura).
- Task 2: gerar o build da extensão e registrar no `08-VALIDATION.md` o roteiro manual D-20 com o resultado de cada
  passo (preenchido a partir da conferência humana consolidada no `/gsd-verify-work`).

**3. Riscos de cada ação**
- Task 1 — rodar testes do backend que falam com o Supabase real e exigem `.env` (`test_schema.py`,
  `conftest.supabase_client`).
- Task 1 — dar a fase por verde com alguma decisão do time não aplicada (critério não atendido).
- Task 2 — o executor ler `.env` para subir o backend local.
- Task 2 — marcar o manual como aprovado sem a pessoa ter feito.

**4. Como prevenir**
- Rodar só a lista explícita de testes puros da fase.
- Conferir nos SUMMARYs dos planos com checkpoint (08-07, 08-08, 08-09, 08-13, 08-15, 08-18) qual opção foi
  escolhida; qualquer critério do ROADMAP não atendido por causa de uma decisão (ex.: B1 rejeitada → critério 1) é
  listado como pendência no `08-VALIDATION.md`, nunca omitido.
- O roteiro manda a pessoa subir o backend como na Fase 7 (ela mesma, com o `.env` dela); o executor nunca abre
  `.env`.
- O manual é `human-check` (consolidado no fim da fase); o documento só recebe "aprovado" com o retorno da pessoa.

**5. Como consertar (plano de rollback)**
- Só documentação: `git revert` do commit do `08-VALIDATION.md`. Falha no portão → voltar ao plano dono do teste
  vermelho (não corrigir aqui).

**6. Decisões que são do usuário/time**
- O resultado do teste manual D-20 é da pessoa que o executa; pendências de decisões do time (B1–B5) ficam
  registradas como bloqueios do encerramento.
- Pendência herdada da Fase 6 (não bloqueia esta fase, mas fica visível): ativar `EXTENSION_SHARED_KEY` no Railway.

**7. Verificação (ponta a ponta)**
- Automático: `cd taqciti && npm test && npm run typecheck && npm run lint && npm run build`; backend: lista de
  testes puros da fase; diff vazio nos manifestos de pacote.
- Manual: roteiro D-20 (a)-(d) + backstops + `getBytesInUse` (abaixo).
