## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
Hoje a Taqciti não tem como perguntar ao Agente "quais clientes existem?" nem pedir "abra uma sessão nova
para esta reunião" — as rotas que existem são do web app ou do CITi Flow. Este plano primeiro pergunta ao time
se podemos criar essas portas de entrada novas (é uma mudança de contrato, decisão B1). Se sim, criamos duas
portas exclusivas da extensão, com a mesma "senha" opcional já usada pelo envio de transcrição: uma que
devolve só o nome do cliente e do projeto (nada de contexto ou orçamento), e outra que abre uma sessão nova
para um cliente. A terceira porta (criar cliente) depende também da decisão B2 e fica no plano 08-12.

**2. Como vai ser alterado**
- Task 1: `checkpoint:decision` B1 — nada é escrito antes da resposta do time.
- Task 2 (commit): novos `backend/app/models/extension.py` (os três schemas), `backend/app/repositories/
  extension_repository.py` (`list_clients`), `backend/app/services/extension_session_service.py`
  (`list_clients`), `backend/app/routers/extension_clients.py` (GET `/webhook/extension/clients`) e
  `backend/tests/test_extension_clients.py`.
- Task 3 (commit): `ExtensionRepository` ganha `get_project_id` e `insert_session`; o service ganha
  `create_session`; o router ganha POST `/webhook/extension/sessions`; registro do router em
  `backend/app/routers/__init__.py` (1 linha + `__all__`) e `backend/app/main.py` (import + `include_router`);
  testes estendidos. Toca 6 arquivos, dois deles só com as linhas de registro.
Tudo é código novo; nenhum router existente (`projects.py`, `sessions.py`, `webhook.py`) é modificado.

**3. Riscos de cada ação**
- Task 1 — o executor escolher pelo time (contrato de API, CLAUDE.md "Não decida o que é do time").
- Task 2 — a listagem vazar dados (contexto pré-reunião, orçamento) para quem tiver a URL e a chave.
- Task 2 — colisão de rota com o `POST /webhook/extension` existente.
- Task 2 — lógica de negócio ou `db.table()` no router.
- Task 3 — reutilizar `POST /sessions/start` (CITi Flow, segredo no Vault a cada chamada) por conveniência.
- Task 3 — sessão para projeto inexistente virar 500 (a extensão trataria como "tentar de novo").
- Task 3 — esquecer o registro do router (rota 404 em produção) ou registrar no lugar errado.
- Todas — rotas de escrita abertas quando `EXTENSION_SHARED_KEY` não está definida (gate opt-in) — qualquer
  pessoa com a URL cria sessões.

**4. Como prevenir**
- Task 1 é `gate="blocking-human"` sem `auto_select`: nunca aprovada sozinha.
- `ExtensionClientResponse` com exatamente `id`, `client`, `name`; o repositório faz
  `select("id, client, name")`; teste confere as chaves da resposta.
- Prefixo `/webhook/extension` com caminhos `/clients` e `/sessions` (sem `POST ""`); teste lista as rotas do
  `APIRouter` e confere que não há rota vazia.
- Router só chama `service.*`; grep negativo de `db.table` no router.
- O service usa apenas `ExtensionRepository`; grep negativo de `/sessions/start` e `citiflow` nos arquivos
  novos.
- `create_session` levanta `HTTPException(404, "Project not found")` quando `get_project_id` devolve `None`;
  teste.
- Teste de registro: `from app.main import app` não é usado (sobe tudo); em vez disso grep de
  `include_router(extension_clients_router)` + o `__all__`.
- Risco do gate opt-in é decisão do time na Task 1: na opção recomendada a resposta tem que trazer o DONO do risco
  residual T-08-10 e a condição de revisão (ex.: "até ativar `EXTENSION_SHARED_KEY` no Railway"); sem isso o
  executor não escreve rota nenhuma e pede o dado. O plano 08-21 confere esse registro no fechamento da fase.

**5. Como consertar (plano de rollback)**
- Task 2/Task 3: `git revert <sha>` remove as rotas; nada mais do backend depende delas. Se já estiver em
  produção, um novo deploy sem o commit retira as rotas — a Taqciti volta a cair no plano B (o diretório HTTP
  trata 404/erro como "lista indisponível").
- Nenhuma migração, nenhum dado alterado; sessões já criadas pelas rotas continuam válidas e aparecem no web
  app como qualquer sessão `extension`.

**6. Decisões que são do usuário/time**
- **DECISÃO EM ABERTO B1 — PARAR na Task 1 até o time decidir** (contrato da API: rotas novas, D-13/D-16).
- **DECISÃO EM ABERTO B4-a — dentro do mesmo checkpoint:** `mode` do cliente criado pela Taqciti (`discovery`

  vale. Aceitar risco de segurança é do time, nunca do executor.
- D-17 (GET `/projects`/`/sessions` abertos) já foi decidido pelo usuário: este plano não os altera.
