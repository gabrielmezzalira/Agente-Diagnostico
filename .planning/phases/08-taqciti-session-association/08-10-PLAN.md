## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
Até aqui existem a "etiqueta de destino" de cada reunião (08-01), as telas soltas (08-02/03/04) e a esteira de
envio (08-05). Este plano cria os "botões de comando" que as telas vão apertar e o que acontece quando são
apertados: "mostre os clientes", "abri o aviso", "deixa para depois" e "vincule". Vincular faz, em ordem: cria o
cliente (se for novo), abre uma sessão nova no Agente, manda tudo o que já foi falado em blocos e, só no fim,
libera o envio ao vivo — assim a reunião inteira vai para o mesmo lugar e nada se perde nem se repete. Se a
reunião já acabou, "vincular" vira "enviar a reunião guardada". Enquanto as rotas do backend (decisão B1) não
existem, a lista responde "indisponível" e a pessoa usa o código da sessão (plano B) — que já funciona de ponta
a ponta depois deste plano.

**2. Como vai ser alterado**
Três commits:
- Task 1: novo `taqciti/src/shared/types/agenteMessages.ts` (schemas de `clients/list`, `meeting/open`,
  `meeting/defer`, `meeting/bind` + resultado), `messages.ts` passa a espalhar esses schemas na união
  `uiMessageSchema` (mecânico, 2 linhas), novo `agenteAssociationService.ts` (`listClients`/`open`/`defer`) com
  teste.
- Task 2: novo `agenteBindFlow.ts` (vínculo ao vivo: manual e cliente) com teste; `agenteAssociationService.ts`
  ganha `bind`; nova raiz de composição `agenteAssociation.ts` (portas indisponíveis por padrão,
  `configureAgenteAssociation` como seam de teste); `index.ts` ganha os 4 `case`s, cada um só delegando.
- Task 3: `agenteBindFlow.ts` ganha o envio da reunião encerrada (`ended-unsent → sending → sent|send-failed`),
  com teste.
Também na Task 2, duas regras de borda do vínculo ao vivo: depois de `link-completed` o fluxo chama a dependência
`onLinked` (produção: `reevaluateAgenteStreamer`, exportada pelo 08-01) para o resto do que foi dito sair mesmo sem
flush novo; e, se a reunião já terminou quando a criação da sessão falha, o fluxo aplica `meeting-ended` logo depois
de `link-failed` (→ `ended-unsent`). Na Task 3, os eventos do envio em partes seguem o estado atual da associação
(`linking` → `link-*`, `sending` → `send-*`), porque a mesma sala pode ser retomada no meio do envio.

**3. Riscos de cada ação**
- Task 1 — schema frouxo deixar passar `meetingId` gigante ou campos inesperados; `messages.ts` crescer demais.
- Task 1 — `open`/`defer` aplicados em estado errado (ex.: reabrir uma reunião já vinculada).
- Task 2 — criar sessão a cada clique / dois cliques criarem duas sessões (sessões órfãs no Agente).
- Task 2 — service worker morrer entre o POST da sessão e a gravação → segunda sessão na nova tentativa.
- Task 2 — o envio ao vivo começar antes de terminar o que já foi falado → ordem invertida na transcrição.
- Task 2 — enviar para a sessão errada (cliente A no relatório de B).
- Task 2 — lógica no `index.ts`.
- Task 2 — o comando segurar a resposta até o fim do envio (painel "travado"; resposta perdida se o painel fechar).
- Task 2 — a reunião terminar durante o vínculo e as palavras ditas depois do snapshot nunca saírem (nenhum flush
  novo depois de `link-completed`).
- Task 2 — a reunião terminar durante o vínculo, a criação da sessão falhar e a associação ficar em `deferred` de uma
  reunião que já acabou (o cartão do fim nunca apareceria).
- Task 3 — reenviar uma reunião já enviada ou em `send-failed` do zero (duplicata em massa).
- Task 3 — rajada no backend.
- Task 3 — a mesma sala ser retomada no meio do envio da reunião encerrada (associação vira `linking`, 08-22) e o
  fluxo aplicar `send-completed`/`send-progress` num estado que não aceita — a reunião ficaria sem destino ao vivo.
- Todas — gravar a chave `x-agente-key` em algum estado persistido.

**4. Como prevenir**
- `z.string().min(1).max(200)` para ids, `trim().min(1).max(120)` para nome, regex de UUID para o ID manual;
  schemas num arquivo próprio para `messages.ts` só ganhar o espalhamento.
- Transições validadas pelo reducer (08-01): evento ilegal → `{ ok: false, error: 'invalid-state' }`.
- `link-started`/`send-started` gravados ANTES de criar a sessão, pela fila serializada do store: o segundo
  comando vê `linking`/`sending` e recebe `invalid-state`; teste com dois `bind` em `Promise.all` e o gateway
  contando 1 chamada.
- Recuperação de boot trata `linking` sem sessão → `deferred` + erro (plano 08-22, Task 2; até ele entrar, nenhuma
  associação nasce sozinha em produção, então não há `linking` a recuperar).
- Ao vivo, a associação fica `linking` (streamer em `hold`) até o envio em partes terminar; `link-completed` grava
  `linked` + `seedSent` numa única escrita.
- O `sessionId` vem da porta (ou do ID manual validado) e é gravado na associação; os requests são montados com
  `buildExtensionChunkRequest({ ...config, agenteSessionId: sessionId }, …)`; teste confere o `session_id` de
  cada corpo.
- `index.ts`: cada `case` é uma linha `return agenteAssociation.<método>(...)`.
- `bind` devolve `{ ok: true }` logo depois de a sessão existir e dispara o envio com `void` + log de erro;
  teste confere que a resposta chega antes do fim do envio.
- Task 2: `onLinked(meetingId)` é chamado depois de `link-completed` (o passo do streamer entra na fila serializada
  dele, então não duplica com um flush que chegue junto); teste "reunião encerrada durante o vínculo → resto enviado
  uma vez".
- Task 2: depois de `link-failed`, se `getMeetingState()` mostra que aquela reunião não está mais ao vivo, aplicar
  `meeting-ended` (o reducer do 08-01 leva `deferred` a `ended-unsent` preservando o erro); teste.
- Task 3 aceita só `ended-unsent`; `send-failed` → `invalid-state` (retomar é decisão B3, plano 08-20).
- Task 3: uma função interna escolhe o evento pelo estado atual lido do store antes de cada aplicação (`linking` →
  `link-progress`/`link-completed`/`link-failed`; `sending` → `send-*`); quando concluir em `linking`, chama
  `onLinked`; teste com `meeting-resumed` aplicado no meio do envio.
- Esteira serial com blocos/pausa do 08-05.
- A chave só existe na hora de montar o request (config atual); nenhum estado guarda headers (lista branca do
  store, 08-01).
