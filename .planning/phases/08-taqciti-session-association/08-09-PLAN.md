## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
Quando a internet falha no meio de um envio, a Taqciti não sabe se a fala chegou ou não — e, ao tentar de
novo, pode gravar a mesma fala duas vezes no Agente. A solução proposta é dar a cada fala um "número de série"
(o `chunk_id`): se a mesma fala chegar de novo, o Agente reconhece o número e ignora a cópia, como um caixa que
não cobra duas vezes o mesmo código de barras. Isso exige uma coluna nova no banco de produção (decisão do
time, B3) e uma mudança no contrato do webhook. A migração é feita por uma pessoa do time no Supabase, fora do
repositório.

**2. Como vai ser alterado**
- Task 1: `checkpoint:decision` B3.
- Task 2, em **dois commits**: (a) **refactor mecânico** — o `insert` direto de `extension_webhook` vai para o
  novo `backend/app/repositories/transcript_chunks_repository.py` (`insert_chunk`), sem mudar comportamento;
  (b) **comportamento** — a migração `supabase/migrations/20261011000000_add_chunk_id_to_transcript_chunks.sql`,
  `chunk_id` opcional em `ExtensionChunk`, deduplicação no repositório e no webhook, teste novo
  `test_webhook_idempotency.py` e atualização de `test_extension_chunk_extra_fields.py` (que provava que o campo
  era ignorado — agora ele passa a ser gravado).
- Task 3: `checkpoint:human-action` [BLOCKING] — aplicar a migração no Supabase de produção e conferir.
`/webhook/recall` não é tocado.

**3. Riscos de cada ação**
- Task 1 — decidir pelo time (contrato do webhook + migração em produção).
- Task 2a — o refactor mudar o que é gravado (ex.: perder o `strip` do texto).
- Task 2b — o backend com o código novo ir para produção ANTES da migração: inserts com `chunk_id` falham (coluna
  inexistente) → 500 em toda fala que traga o campo.
- Task 2b — tratar qualquer `APIError` como duplicata e engolir erro real (perda silenciosa).
- Task 2b — a suposição A2 (`APIError.code == "23505"`) estar errada → duplicata vira 500 e a nova tentativa
  nunca termina.
- Task 2b — índice único bloquear linhas antigas ou o `/webhook/recall` (que não manda `chunk_id`).
- Task 3 — aplicar a migração errada / no projeto errado, ou expor credenciais ao aplicar.

**4. Como prevenir**
- Task 1 com `gate="blocking-human"`.
- Task 2a: rodar `test_extension_chunk_extra_fields.py` antes e depois sem mudar o teste (prova de refactor
  puro).
- Task 2b: o repositório só inclui a chave `chunk_id` na linha quando ela vem preenchida (clientes antigos e
  o recall continuam gravando exatamente como hoje); a Taqciti só passa a mandar o campo no plano 08-19, que tem
  como pré-condição a Task 3 concluída; a ordem de rollout fica escrita no SUMMARY: migração → deploy do
  backend → build da Taqciti.
- Só `exc.code == "23505"` vira `False`; qualquer outro erro é relançado; teste com fake de `APIError` de
  outro código.
- Teste com fake de `APIError(code="23505")` + verificação real no D-20 (b) contra o Supabase (a suposição A2
  fica marcada para conferência).
- No Postgres, NULLs são distintos em índice único: linhas sem `chunk_id` nunca colidem; a migração usa `IF NOT
  EXISTS` (idempotente).
- Task 3: o roteiro manda usar o SQL Editor do projeto de produção (ou `supabase db push` com
  `SUPABASE_ACCESS_TOKEN` definido pela própria pessoa no terminal dela); o executor NUNCA lê `.env`; consultas de
  conferência prontas.

**5. Como consertar (plano de rollback)**
- Task 2a: `git revert <sha-2a>` (refactor puro, sem efeito externo).
- Task 2b: `git revert <sha-2b>` — o webhook volta a ignorar `chunk_id`; a coluna/índice no banco ficam
  inofensivos (nada lê). Para remover do banco, uma pessoa roda no SQL Editor:
  `DROP INDEX IF EXISTS ux_transcript_chunks_session_chunk; ALTER TABLE transcript_chunks DROP COLUMN IF EXISTS
  chunk_id;` (perde apenas os ids, nenhuma transcrição).
- Se o backend novo for publicado antes da migração e der 500: aplicar a migração (Task 3) resolve; ou novo
  deploy sem o commit 2b.

**6. Decisões que são do usuário/time**
- **DECISÃO EM ABERTO B3 — PARAR na Task 1 até o time decidir** (contrato do webhook + migração no banco de
  produção, D-19).
- **Ação humana fora do repo (Task 3):** aplicar a migração no Supabase de produção. O executor não tem e não
  pode buscar as credenciais.
- Suposição A7 registrada: `chunk_id` como `text` (aceita `bulk:{meetingId}:{index}` e UUIDs); se o time preferir
  outro tipo, a Task 2b muda só a migração.
