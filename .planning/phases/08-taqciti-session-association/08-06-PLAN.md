## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
Quando a primeira fala de uma reunião chega ao Agente, ele monta o "cérebro" daquela sessão (o pipeline que
classifica cobertura e procura alertas). Hoje, se duas falas chegam quase juntas, ele pode montar DOIS cérebros
para a mesma reunião, e um deles fica rodando sozinho, gastando a IA sem ninguém ver. Colocamos uma "fila de
uma porta só" por sessão: a segunda fala espera a primeira terminar de montar e usa o mesmo cérebro. Também
escrevemos um teste que prova que o Agente atual não quebra se a Taqciti mandar um campo a mais (o
`chunk_id`) — isso ajuda o time na decisão B3, sem mudar nada em produção.

**2. Como vai ser alterado**
Dois commits:
- Task 1 (correção, comportamento): `backend/app/services/pipeline.py` — `PipelineManager` ganha um dicionário
  de `asyncio.Lock` por `session_id`; o corpo atual de `get_or_create` passa a rodar dentro do lock, com a
  checagem "já existe em `_pipelines`?" repetida depois de adquirir. Novo teste
  `backend/tests/test_pipeline_get_or_create_lock.py`.
- Task 2 (só teste): novo `backend/tests/test_extension_chunk_extra_fields.py`. Nenhum código de produção muda.

**3. Riscos de cada ação**
- Task 1 — deadlock ou lentidão: o lock global serializaria todas as sessões.
- Task 1 — `stop_session` concorrente com `get_or_create` deixar o pipeline registrado de uma sessão encerrada.
- Task 1 — regressão no caminho `allow_finished=True` (relatório de sessão encerrada).
- Task 1 — crescimento sem fim do dicionário de locks.
- Task 1 — misturar esta correção com refator do arquivo (o `get_or_create` é grande).
- Task 2 — o teste depender de rede/`.env`.

**4. Como prevenir**
- Lock por chave (`self._locks.setdefault(session_id, asyncio.Lock())`); teste com duas sessões diferentes em
  paralelo provando que uma não espera a outra.
- O lock só protege a criação; `stop_session` continua idempotente (já coberto por
  `test_finish_stops_pipeline.py`, que precisa continuar verde).
- Teste do caminho encerrado com fake de `sessions.status = 'finished'`: devolve pipeline e não registra.
- Remover a entrada de `self._locks` quando a criação devolve `None` (sessão inexistente/encerrada) e em
  `stop_session` (1 linha); comentário explicando.
- Commit único de correção, sem renomear nem mover o resto do método (CLAUDE.md: correção ≠ refator).
- Testes puros com `monkeypatch` de `get_supabase`/`llm_service`/`extract_structured_context` e `pipeline.start`
  (estilo `test_finish_stops_pipeline.py`); não usar `conftest.supabase_client`.

**5. Como consertar (plano de rollback)**
- Task 1: `git revert <sha-task-1>` devolve o `get_or_create` sem lock (risco antigo de pipeline duplicado
  volta). Sem migração, sem dado afetado. Em produção, o rollback é um novo deploy do backend.
- Task 2: `git revert <sha-task-2>` remove só o teste.

**6. Decisões que são do usuário/time**
- Nenhuma DECISÃO EM ABERTO: mudança interna sem contrato (mapa do RESEARCH: "L — backend, sem contrato").
- A decisão B3 (usar ou não `chunk_id`) continua com o time (plano 08-09); a Task 2 só produz evidência.
- Risco conhecido e aceito, registrado: o `insert` síncrono do supabase-py dentro de `async def` bloqueia o
  event loop por chunk (Pitfall 5a); a mitigação desta fase é o envio serial com pausa (plano 08-05). Trocar
  por `asyncio.to_thread` fica para outra discussão.

**7. Verificação (ponta a ponta)**
- `cd backend && python -m pytest tests/test_pipeline_get_or_create_lock.py -x -q` (teste semente:
  `asyncio.gather` de duas chamadas → 1 pipeline, 1 `start`).
- `cd backend && python -m pytest tests/test_extension_chunk_extra_fields.py tests/test_finish_stops_pipeline.py tests/test_webhook_auth.py -x -q`.
