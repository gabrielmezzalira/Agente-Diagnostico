## Plano em 7 seções (obrigatório — CLAUDE.md §"Regras de Planejamento de Tasks")

**1. O que muda (em linguagem comum)**
O time já decidiu (B3) como lidar com o risco de fala duplicada. Agora a Taqciti passa a colar o "número de série"
em cada fala que manda (se essa foi a decisão) e liga a chave que estava desligada: quando o Agente cair, as falas
ficam no caderno da Taqciti e são reenviadas, na ordem, quando ele voltar — e o painel avisa enquanto isso. Se o
backend já tinha recebido uma fala cuja resposta se perdeu, o número de série faz o Agente ignorar a cópia.

**2. Como vai ser alterado**
Dois commits:
- Task 1 (só se B3 = aprovar-chunk-id): `buildExtensionChunkRequest` ganha `chunkId` opcional
  (`agenteConfig.ts`, ~3 linhas); `outbox.ts` ganha `AGENTE_SEND_CHUNK_ID = true` e `buildOutboxRequest` passa
  `item.chunkId`; `agenteBindFlow.ts` passa `part.chunkId`; testes.
- Task 2: `outbox.ts` troca `AGENTE_OUTBOX_RESEND_ENABLED` para `true`; `agenteSender.test.ts` passa
  `resendEnabled: false` explícito nos casos que testam o comportamento antigo; `agenteOutbox.test.ts` passa a
  esperar o reenvio no padrão de produção.

**3. Riscos de cada ação**
- Task 1 — mandar `chunk_id` para um backend sem a coluna (migração não aplicada) → 500 em todo envio.
- Task 1 — gerar id novo a cada tentativa (dedup não funciona).
- Task 2 — reenvio sem dedup (opção reenvio-sem-chunk-id) duplicar falas (risco aceito pelo time).
- Task 2 — testes antigos dependerem do padrão desligado e quebrarem.
- Task 2 — ligar o reenvio ativa de fato a regra de retirada por HTTP 500 (B3-b): se o valor aplicado no 08-23 não
  for o que o time respondeu, a Taqciti desiste de falas (ou trava a fila) sem o time ter aceitado.

**4. Como prevenir**
- Pré-condição: a migração foi confirmada no 08-09 Task 3; o rollout fica migração → deploy do backend → build
  da Taqciti (registrado no 08-09-SUMMARY).
- O `chunkId` nasce uma vez (outbox ao vivo; determinístico em partes) e é persistido; teste confere o mesmo id
  antes e depois de um reinício.
- Opção reenvio-sem-chunk-id: o risco foi aceito explicitamente pelo time no checkpoint; registrado no SUMMARY.
- Casos antigos passam `resendEnabled: false` explícito; o gate roda os dois arquivos inteiros.
- Pré-condição da Task 2: o 08-23-SUMMARY registra `AGENTE_OUTBOX_SERVER_ERROR_MAX_AGE_MS` igual à resposta B3-b do
  08-09-SUMMARY (o teste do 08-23 que fixa esse valor roda no gate desta task); toda fala descartada continua indo
  para o rastro `taq:agenteDropTrace`, visível na tela "Agente Diagnóstico".

**5. Como consertar (plano de rollback)**
- Task 2: `git revert <sha-task-2>` desliga o reenvio (volta ao comportamento da Fase 7, com fila durável).
- Task 1: `git revert <sha-task-1>` para de mandar `chunk_id` (o backend aceita os dois formatos).

**6. Decisões que são do usuário/time**
- Implementa a **decisão B3** registrada no 08-09-SUMMARY (pré-condições abaixo): `aprovar-chunk-id` → Tasks 1 e
  2; `reenvio-sem-chunk-id` → só a Task 2; `adiar` → nada executa e o critério 4 fica pendente (escalar).
- **DECISÃO EM ABERTO B3-b (já respondida no mesmo checkpoint do 08-09):** este plano não muda a regra de retirada
  por HTTP 500 — só a liga junto com o reenvio, com o valor que o 08-23 aplicou a partir da resposta do time.

**7. Verificação (ponta a ponta)**
- `cd taqciti && npx vitest run src/shared/config/agenteConfig.test.ts src/background/agenteBindFlow.test.ts` (Task 1).
- `cd taqciti && npx vitest run src/background/agenteSender.test.ts src/background/agenteOutbox.test.ts` — teste
  semente: padrão de produção → Agente cai → offline com contagem → reinício → volta → reenvio na ordem com os
  mesmos chunk_id.
- D-20 (b), no fim da fase: derrubar o backend local durante a reunião, religar, conferir no banco sem duplicatas.
